## 2. User Roles & Access Control

The system implements a **multi-guard, multi-role** authentication and authorization model across three dedicated database tables (`users`, `sellers`, `riders`), resolved via `App\Http\Middleware\RoleMiddleware`.

```
                    +-----------------------+
                    |    RoleMiddleware     |
                    +-----------+-----------+
                                |
        +-----------------------+-----------------------+
        |                       |                       |
+-------v-------+       +-------v-------+       +-------v-------+
|  User Guard   |       |  Seller Guard |       |  Rider Guard  |
|  table: users |       | table: sellers|       | table: riders |
+-------+-------+       +---------------+       +---------------+
        |
  [sellerType]
   |        |
   |        +---> sellerType == 1: Admin
   +------------> sellerType == 2: Buyer / Customer
```

### Role Breakdown

| Role | Guard & Table | Authorization Criterion | Core Capabilities |
| :--- | :--- | :--- | :--- |
| **Customer (Buyer)** | Guard: `web`<br>Table: `users` | `Auth::guard('web')->check()` && `user->sellerType != 1` (default: `2`) | - Register with 6-digit email OTP<br>- Browse verified, open shops by sector/landmark<br>- Search products across shops and categories<br>- Maintain single-seller cart with stock validation<br>- Apply promo codes & checkout (COD / online)<br>- Real-time order tracking & order cancellation<br>- Buy again (1-click reorder into cart)<br>- Order-based chat with seller<br>- Order feedback and 1-5 star ratings<br>- Favorite/bookmark shops and products |
| **Seller (Merchant)**| Guard: `seller`<br>Table: `sellers` | `Auth::guard('seller')->check()` && `seller->accountIsApproved == 1` | - Register shop (sector, near areas, category)<br>- Await admin approval (`accountIsApproved`)<br>- Submit verification documents for KYC<br>- Configure operating hours (`opens_at`, `closes_at`, `is_open`)<br>- Import master catalog products into shop inventory<br>- Set custom prices, update stock levels, toggle availability<br>- Bulk adjust prices (% markup / markdown or reset to base)<br>- Manage incoming orders: Accept, Prepare, Ready for Pickup<br>- Chat with buyer regarding an active order<br>- View earnings report (all-time, week, month, year) with 6-month chart |
| **Rider (Delivery Partner)**| Guard: `rider`<br>Table: `riders` | `Auth::guard('rider')->check()` && `rider->is_approved == 1` | - Register with vehicle details, CNIC & document uploads<br>- Await admin document verification (`is_approved`)<br>- Toggle online/offline shift status<br>- View available orders ready for pickup (`ready_for_pickup`)<br>- Claim/accept an order (`assigned_to_rider`)<br>- Update delivery status (`picked_up`, `delivered`)<br>- Upload delivery proof photo on completion<br>- View daily completed order count and delivery earnings |
| **Administrator** | Guard: `web`<br>Table: `users` | `Auth::guard('web')->check()` && `user->sellerType == 1` | - Dashboard analytics (gross revenue, order counts, 7-day volume chart)<br>- Unified moderation queue for pending sellers, riders, products, and reviews<br>- Manage master product catalog (categories, global products, base prices)<br>- Dispatch background price sync job (`SyncProductPriceUpdate`)<br>- Manage promo codes (fixed/percentage, min order, usage caps)<br>- Review and approve/reject seller verification applications<br>- Cryptographically signed seller impersonation (`loginAsSeller`) and return-to-admin |

## 4. Response Format Analysis & Mobile API Migration Plan

### 4.1. Currently Returning JSON (Ready for Mobile with minor formatting)
Only **4 controllers** contain methods that currently return JSON responses:
1. `GET /search-products` (`ProductController@searchProducts`): Returns `{ products: [...] }` with `shop_product_id`, `seller_id`, `name`, `price`, `stock_quantity`.
2. `GET /rider/available-orders` (`RiderController@availableOrders`): Returns an array of order objects with seller details for riders.
3. `POST /chat/{order}/send` & `POST /seller/chat/{order}/send` (`MessageController@send`): Returns `{ success: true, message: {...} }` when `Accept: application/json` is sent.
4. `POST /chat/{order}/read`, `POST /seller/chat/{order}/read`, `GET /chat/{order}/messages`, `GET /seller/chat/{order}/messages` (`MessageController`): Returns `{ success: true, messages: [...] }`.

### 4.2. Currently Returning Blade Views / Web Redirects (Must be Converted)
All remaining 100+ routes return Blade views or HTTP redirects (`redirect()->back()` or `redirect()->route(...)`) backed by session state.

### 4.3. API Conversion Blueprint for Mobile App

To support a mobile app (Flutter, React Native, iOS/Android), create an `api/v1` namespace with standardized JSON responses:

```json
{
  "success": true,
  "data": {},
  "message": "Human readable confirmation",
  "meta": {}
}
```

#### Endpoints Required for Customer App (`/api/v1/customer/`)
- `POST /auth/register` (Returns user object + bearer token or requires OTP)
- `POST /auth/verify-otp` (Payload: `email`, `otp`; Returns Sanctum token + user profile)
- `POST /auth/login` (Returns Sanctum token + user profile)
- `POST /auth/logout` (Revokes current access token)
- `GET /profile` & `PUT /profile` (Includes multipart avatar upload)
- `GET /home` (Categories list, open sellers in user sector, top ratings)
- `GET /sellers/{id}` (Seller profile, operating hours status, catalog products categorized)
- `GET /sellers/{id}/products/{listing_id}` (Single product detail)
- `GET /search?q={query}&sector={sector}` (Live shop/product search)
- `POST /cart/validate` (Replaces session cart: client passes cart array; server validates stock, seller consistency, and computes subtotal/delivery)
- `POST /checkout/apply-promo` (Validates promo code against cart subtotal)
- `POST /orders` (Places order, reserves stock, dispatches notifications; returns created order object)
- `GET /orders/active` (Orders currently in progress)
- `GET /orders/history` (Completed and cancelled orders with pagination)
- `GET /orders/{id}` (Full order details, items, seller info, assigned rider)
- `POST /orders/{id}/cancel` (Allows cancellation if `pending` or `confirmed_by_seller`)
- `POST /orders/{id}/feedback` (Submit rating 1-5 & comment)
- `POST /favorites/sellers/{id}` & `POST /favorites/products/{id}` (Toggle favorites)
- `GET /notifications` & `POST /notifications/read`

#### Endpoints Required for Rider App (`/api/v1/rider/`)

## 5. Authentication Architecture & Sanctum Migration

### Current State
1. **Engine:** Traditional Laravel session cookies (`laravel_session`, `XSRF-TOKEN`).
2. **Guards:** Three parallel session guards defined in `config/auth.php`:
   - `web` -> `User` model
   - `seller` -> `Seller` model
   - `rider` -> `Rider` model
3. **Session Dependency:** Customer OTP verification stores `otp_user_id` in session (`session(['otp_user_id' => $user->id])`), which fails in stateless REST APIs.
4. **Cart Dependency:** Cart is stored entirely in PHP sessions (`Session::get('cart')`).

### Migration to Token-Based Auth (Sanctum)

`laravel/sanctum` is already installed (`^4.2`), and the `personal_access_tokens` table already exists in the database.

#### Step 1: Enable API Routing in Laravel 11
Edit `bootstrap/app.php` to register the `api.php` route file:
```php
return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        api: __DIR__.'/../routes/api.php', // <-- Enable this line
        commands: __DIR__.'/../routes/console.php',
        health: '/up',
    )
    // ...
```

#### Step 2: Model Setup
`App\Models\User`, `App\Models\Seller`, and `App\Models\Rider` already import `Laravel\Sanctum\HasApiTokens`.

#### Step 3: Sanctum Token Generation Pattern
In login and registration controllers, issue scoped personal access tokens:

```php
// Customer Login (AuthController)
if (Auth::attempt($credentials)) {
    $user = Auth::user();
    if (!$user->is_verified) {
        return response()->json(['error' => 'Please verify your OTP first.'], 403);
    }
    $token = $user->createToken('customer-app', ['role:customer'])->plainTextToken;
    return response()->json(['token' => $token, 'user' => $user]);
}

// Seller Login (SellerController)
$seller = Seller::where('email', $request->email)->first();
if ($seller && Hash::check($request->password, $seller->password)) {
    if (!$seller->accountIsApproved) {
        return response()->json(['error' => 'Account pending admin approval.'], 403);
    }
    $token = $seller->createToken('seller-app', ['role:seller'])->plainTextToken;
    return response()->json(['token' => $token, 'seller' => $seller]);
}

// Rider Login (RiderAuthController)
$rider = Rider::where('email', $request->email)->first();
if ($rider && Hash::check($request->password, $rider->password)) {
    if (!$rider->is_approved) {
        return response()->json(['error' => 'Rider account not approved by admin.'], 403);
    }
    $token = $rider->createToken('rider-app', ['role:rider'])->plainTextToken;
    return response()->json(['token' => $token, 'rider' => $rider]);
}
```

#### Step 4: Stateless OTP Verification
Refactor `verifyOtp` to accept `email` and `otp` directly in the request payload rather than reading `session('otp_user_id')`:
```php
public function verifyOtp(Request $request)
{
    $request->validate([
        'email' => 'required|email|exists:users,email',
        'otp'   => 'required|digits:6',
    ]);

    $user = User::where('email', $request->email)->first();

    if (!$user || $user->otp !== $request->otp || Carbon::parse($user->otp_expires_at)->isPast()) {
        return response()->json(['error' => 'Invalid or expired OTP.'], 422);
    }

    $user->update([
        'is_verified' => true,
        'otp' => null,
        'otp_expires_at' => null,
    ]);

    $token = $user->createToken('customer-app', ['role:customer'])->plainTextToken;

    return response()->json([
        'success' => true,
        'message' => 'Account verified successfully.',
        'token'   => $token,
        'user'    => $user,
    ]);
}
```

#### Step 5: Multi-Guard Sanctum Resolution
Because Sanctum's `personal_access_tokens` table is polymorphic (`tokenable_type` = `App\Models\User`, `App\Models\Seller`, or `App\Models\Rider`), incoming `Authorization: Bearer <token>` requests automatically hydrate the correct model on `$request->user()`. Middleware can enforce role permissions via abilities:
```php
Route::middleware(['auth:sanctum', 'ability:role:customer'])->group(function () {
    Route::post('/checkout', [ApiOrderController::class, 'placeOrder']);
});
```

## 7. Core Business Logic & Workflows

### 7.1. Order Lifecycle & Status State Machine

```
              Customer creates order
                       |
                       v
                 [ pending ] <------------------ Customer can cancel
                       |
          +------------+------------+
          |                         |
          v Seller accepts          v Seller rejects
[ confirmed_by_seller ]       [ rejected ]
   (reserves stock)           (restores stock)
          |
          v Seller prepares
    [ preparing ]
          |
          v Seller packs
  [ ready_for_pickup ] -------> Broadcasts: OrderReadyForPickup (Pusher)
          |
          v Rider accepts
 [ assigned_to_rider ]
          |
          v Rider picks up
    [ picked_up ]
          |
          v Rider delivers (uploads proof)
    [ delivered ]
          |
          v
   [ completed ]
```

1. **Placement:** Buyer checks out; order is created with `status = 'pending'`. Estimated delivery is initialized to `now() + 45 minutes`.
2. **Cancellation Window:** The customer is permitted to cancel the order **only** while in `pending` or `confirmed_by_seller` states.
3. **Seller Acceptance & Stock Reservation:**
   - When the seller changes status to `confirmed_by_seller`, `inventory_reserved_at` is stamped.
   - For every item referencing a `shop_product_id`, the system runs an atomic check:
     ```php
     ShopProduct::whereKey($id)
         ->where('stock_quantity', '>=', $qty)
         ->decrement('stock_quantity', $qty);
     ```
   - If stock is insufficient, the transaction throws an exception and halts confirmation.
4. **Seller Rejection:** If the seller rejects an order that had previously reserved inventory, the stock is automatically restored via `increment('stock_quantity', $qty)`.
5. **Rider Fulfillment:**
   - Once packed, the seller sets `status = 'ready_for_pickup'`. The system broadcasts `App\Events\OrderReadyForPickup` over the private Pusher channel `riders`.
   - Available riders query `/rider/available-orders`.
   - The first rider to click accept claims the order via an atomic condition:
     ```php
     Order::where('id', $orderId)
         ->where('status', 'ready_for_pickup')
         ->whereNull('rider_id')
         ->update(['rider_id' => $rider->id, 'status' => 'assigned_to_rider']);
     ```
   - Rider marks `picked_up`, then `delivered`. When marking `delivered`, the rider optionally uploads a delivery proof photo.

### 7.2. Cart & Pricing Rules
- **Single-Seller Cart Rule:** A buyer can only have items from **one seller** in their cart at any time. Adding an item from another shop requires clearing the cart.
- **Master vs Custom Pricing:**
  - `GlobalProduct` defines a default `base_price`.
  - `ShopProduct` defines an optional `custom_price`.
  - `effective_price` = `$listing->custom_price ?? $listing->globalProduct->base_price`.
- **Promo Code Calculation:**
  - Evaluated against `subtotal = sum(price * quantity)`.
  - Type `percent`: `discount = (subtotal * discount_value) / 100`.
  - Type `fixed`: `discount = discount_value`.
  - If `maximum_discount_amount` is set, `discount = min(discount, maximum_discount_amount)`.
  - Total cannot drop below 0: `payable = max(0, subtotal + deliveryFee - discount)`.
- **Delivery Charges:**
  - In `OrderController`, the delivery charge is currently hardcoded:
    ```php
    $deliveryFee = $subtotal > 0 ? 0 : 0; // Hardcoded to 0
    'delivery_charges' => 0.00
    ```
  - The database column `delivery_charges` supports dynamic fees, and the rider's earnings calculation sums `delivery_charges`.

### 7.3. Store Operating Hours & Open Toggle
- Each merchant has `opens_at` (`TIME`), `closes_at` (`TIME`), and `is_open` (`BOOLEAN`).
- `Seller::isAcceptingOrders()` checks:
  1. If `is_open == false`, store is closed.
  2. If hours are null, store defaults to open.
  3. If `opens_at <= closes_at` (standard daytime): Open if `now() between opens_at and closes_at`.
  4. If `opens_at > closes_at` (overnight shifts): Open if `now() >= opens_at OR now() <= closes_at`.
- If a shop is not accepting orders, product views redirect with a modal alert, and cart adds/checkout attempts are blocked.

### 7.4. Payment Methods
1. **Cash on Delivery (COD):** The default operational mode. `transaction_id` is null.
2. **Online Payment:** Controlled by the configuration `services.payments.online_enabled` (`ONLINE_PAYMENTS_ENABLED` in `.env`, defaults to `false`). When enabled, checkout requires `transaction_id`. Currently no payment gateway SDK (Stripe, JazzCash, EasyPaisa) is integrated.

## 9. File & Media Upload Handling

All uploads are currently stored on the **`public` disk** (`storage_path('app/public')`), which maps to `public/storage/` via the `php artisan storage:link` symlink.

```
storage/app/public/
├── profile_images/          # Customer & Seller avatars (GD-sanitized)
├── products/                # Legacy seller product images
├── global-products/         # Master catalog default SKU images
├── delivery_proofs/         # Rider post-delivery camera snapshots
├── verification_documents/  # Merchant KYC PDF / image uploads
│   └── {seller_id}/
└── rider_docs/              # Rider onboarding documentation
    ├── profile/
    ├── cnic/
    ├── license/
    └── vehicle/
```

### Sanitization & Processing Logic (`App\Support\SanitizedImageUpload`)
To prevent malicious payload injection (such as PHP code hidden inside EXIF metadata):
1. Reads raw bytes via `file_get_contents`.
2. Validates image MIME types using `getimagesizefromstring` (restricts to JPEG, PNG, GIF).
3. Strips metadata by recreating the image on a new true-color canvas via PHP GD:
   ```php
   $image = imagecreatefromstring($contents);
   $canvas = imagecreatetruecolor($width, $height);
   imagecopy($canvas, $image, 0, 0, 0, 0, $width, $height);
   imagejpeg($canvas, null, 85);
   ```
4. Saves as a random UUID filename: `profile_images/{UUID}.jpg`.

*Note for Mobile Apps:* The mobile app should upload files using standard `multipart/form-data`. Max allowed sizes:
- Profile & Product images: `max:2048` (2 MB)
- Delivery proof: `max:4096` (4 MB)
- Seller verification documents: `max:5120` (5 MB, supports PDF)

## 10. Known Bugs, Security Gaps & Hardcoded Logic

During the analysis of the backend source code, the following architectural bugs, security loopholes, and hardcoded values were identified. **These must be addressed when building the API layer:**

### 10.1. Critical Security Gaps
1. **Unverified User Login Allowed (`AuthController.php`):**
   - When a user registers, `is_verified` is set to `false`, and an OTP is emailed.
   - However, `AuthController::login()` validates only credentials (`Auth::attempt($credentials)`) and **does not check `is_verified`**. An unverified user can bypass OTP verification simply by submitting the login form directly.
   - *Fix for API:* Add `if (!$user->is_verified) { return response()->json(['error' => 'Unverified'], 403); }`.
2. **Missing Auth Middleware on Order Review (`web.php` line 205):**
   - Route `POST /order/{id}/feedback` (`OrderController@submitFeedback`) is **not** protected by `auth` middleware in `web.php`.
   - The controller executes `auth()->id()`. If a guest hits this endpoint, `auth()->id()` returns null, causing an unhandled database `QueryException` or creating an orphaned review.
3. **Session Fixation in API Context:**
   - Controllers call `$request->session()->regenerate()`. Stateless API requests without cookies will crash if session drivers are not properly decoupled.

### 10.2. Business Logic Bugs
4. **Inventory Leak on Customer Order Cancellation (`OrderController.php`):**
   - When a seller confirms an order, `reserveCatalogInventory()` decrements stock, and `inventory_reserved_at` is set.
   - If the seller later rejects the order, `restoreCatalogInventory()` increments the stock back.
   - **Bug:** If the *customer* cancels the order (`cancel()` method, line 573) while status is `confirmed_by_seller`, the order status is updated to `cancelled`, but **`restoreCatalogInventory()` is never called**. The reserved stock is permanently lost from the shop's inventory.
5. **Missing `rider_id` in Order Mass Assignment (`Order.php`):**
   - The `$fillable` array in `App\Models\Order` does not contain `'rider_id'`.
   - Direct `$order->update(['rider_id' => $riderId])` or `$order->fill(...)` will silently drop `rider_id`. (In `RiderController`, this works only because it was called on the raw query builder: `Order::where(...)->update(...)`).
   - The `Order` model also lacks a `public function rider()` relationship.
6. **Rider Omitted from Chat Authorization (`MessageController.php`):**
   - `Broadcast::channel('chat.{orderId}')` in `routes/channels.php` explicitly allows riders to listen to order chat.
   - However, `MessageController::send()` and `MessageController::getMessages()` only check `isSeller` or `auth()->id() == $order->user_id`. A rider cannot send or read messages through the controller.
7. **Chat Realtime Broadcasting is Commented Out (`MessageController.php` line 75):**
   - Line 75 contains `// event(new NewMessage($message, $order));` with a comment stating real-time broadcasting was disabled in favor of polling. The chat currently requires polling every few seconds (`/chat/{order}/messages?since=X`).

### 10.3. Hardcoded Values & Geographical Constraints
8. **Hardcoded Karachi / Baldia Town Landmarks (`HomeController.php` lines 59-68):**
   ```php
   $sectorOptions = ['4A', '4B', '4C'];
   $nearAreaOptions = [
       'ABC Swimming Pool',
       'Tajli Noor Masjid',
       'Lahori Hotel',
       'Ali Chowk',
       'Family Park',
       'Carido Hospital',
       'Rubi Mor',
   ];
   ```
   These are hardcoded in the controller instead of being loaded from a `sectors` or `landmarks` database table.
9. **Hardcoded Zero Delivery Fee (`OrderController.php` lines 143, 312, 471):**
   ```php
   $deliveryFee = $subtotal > 0 ? 0 : 0;
   'delivery_charges' => 0.00,
   ```
   Delivery charges are forced to zero regardless of customer distance or order size.
10. **Arbitrary 5 Users Notified on Product Creation (`SellerProductController.php` line 37):**
    ```php
    $users = AppUser::latest()->take(5)->get();
    foreach ($users as $user) {
        $user->notify(new NewServiceAddedNotification(...));
    }
    ```
    When a seller adds a product, notifications are dispatched to exactly the 5 most recently created users in the entire database, regardless of location or preference.
11. **Dormant `Admin` Model:**
    - `App\Models\Admin` exists in the codebase and `config/auth.php` defines an `admins` provider.
    - However, the application uses `User` with `sellerType = 1` for administrators. The `Admin` model is completely unused.
